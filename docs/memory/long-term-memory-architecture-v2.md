# Long-Term Memory: Current Architecture

## Document Scope

This document describes only the long-term memory architecture that is already implemented in the current repo and is actually consumed by the main writing chain.

Historical redesign plans are no longer kept here, nor is the ideal-state blueprint mixed in. The only criterion is: does it actually exist in the current code, and is it wired into the main chain.

## One-Line Conclusion

The real implementation of long-term memory today is:

- `.webnovel/memory_scratchpad.json` as the long-term semantic memory cache
- `index.db`, `summaries/`, `state.json` as the recent-state and historical-evidence layer
- `MemoryOrchestrator` assembles the `working / episodic / semantic` three-layer result
- Then consumed externally by `ContextManager`, `extract_chapter_context.py`, and `MemoryContractAdapter`

It is already a runnable data chain, but not yet a fully independent memory subsystem.

## Data Layers

### 1. Working Memory

Not stored separately at present; assembled temporarily at runtime, mainly from:

- this chapter's outline
- recent chapter summaries
- protagonist state, plot threads, pending disambiguation in `state.json`

This layer is generated by `MemoryOrchestrator._build_working_memory()`.

### 2. Episodic Memory

Mainly from the recent structured evidence in `index.db`, not a separate general historical-retrieval system.

Main sources:

- recent state changes
- recent relationship changes
- recent appearance records

This layer is generated by `MemoryOrchestrator._build_episodic_memory()`, characterized as "recent evidence", not full-corpus semantic recall.

### 3. Semantic Memory

The current core storage of long-term memory is `.webnovel/memory_scratchpad.json`.

It is read/written by `ScratchpadManager`, bucketed by category:

- `character_state`
- `story_facts`
- `world_rules`
- `timeline`
- `open_loops`
- `reader_promises`
- `relationships`

Each memory item uniformly uses the `MemoryItem` structure, with core fields including:

- `id`
- `layer`
- `category`
- `subject`
- `field`
- `value`
- `payload`
- `status`
- `source_chapter`
- `evidence`
- `updated_at`

Supported statuses:

- `active`
- `outdated`
- `contradicted`
- `tentative`

## Write Chain

### 1. Chapter results enter `MemoryWriter`

After a chapter is committed, the writing main chain hands structured results to `MemoryWriter.update_from_chapter_result()`.

Currently implemented write sources include:

- `state_changes`
- `entities_new`
- `relationships_new`
- `chapter_meta.hook`
- `memory_facts`

Among these, `memory_facts` is used for a deeper structured mapping, currently supporting:

- `timeline_events`
- `world_rules`
- `open_loops`
- `reader_promises`

### 2. `ScratchpadManager` does dedup and status convergence

The core rule of `ScratchpadManager.upsert_item()` is:

- compute dedup key by category primary-key rule
- demote the old same-key value to `outdated`
- write the new value as the current effective item
- keep the old value for audit and rollback

Current per-category primary-key rules are uniformly defined in `schema.py`, e.g.:

- `character_state`: `subject + field`
- `relationship`: `subject + field`
- `world_rule`: `subject + field`
- `open_loop`: `subject`

### 3. Compact when over threshold

`ScratchpadManager.save()` calls `compactor.py` when the threshold is reached.

Current compaction strategies include:

- keep only the latest `outdated` per same key
- clean up resolved foreshadowing
- merge overly-old timeline into summary-type `story_fact`
- when total still exceeds limit, do global truncation by status and freshness

### 4. Historical projects can be backfilled

`memory bootstrap` backfills an initial long-term memory from existing `index.db` and `summaries/`.

Currently backfillable content includes:

- character current state
- historical state changes
- recent relationships
- the "foreshadowing" block in summaries

## Read and Orchestration Chain

### 1. `MemoryOrchestrator` owns the unified pack

`MemoryOrchestrator.build_memory_pack()` is the unified read entry point for current long-term memory.

It does four things:

1. build `working_memory`
2. build `episodic_memory`
3. read `active` items from `memory_scratchpad.json`
4. filter, cap, and supplement warnings and stats

Core output fields include:

- `working_memory`
- `episodic_memory`
- `semantic_memory`
- `long_term_facts`
- `active_constraints`
- `recent_changes`
- `warnings`
- `stats`

Among these:

- `semantic_memory` and `long_term_facts` are currently the same batch of directly injectable long-term semantic facts
- `active_constraints` mainly extracts `world_rule` and `open_loop`
- `warnings` currently mainly surfaces memory conflicts

### 2. Current filter rules

`semantic_memory` is not injected in full, but first goes through a light filter.

Existing filter basis:

- whether the memory item's `subject / field / value` appears in this chapter's outline
- whether the source chapter falls within the configured allowed window

Then truncate by budget. The current budget is jointly controlled by `budget.py` and config items.

## Consumption Layer

### 1. `ContextManager`

`ContextManager` is still the overall assembler of writing context.

When `context_use_memory_orchestrator=true`, it will:

- call `MemoryOrchestrator.build_memory_pack()`
- inject the result into the `long_term_memory` section
- then assemble the final context together with `reader_signal / genre_profile / writing_guidance / plot_structure`

So the real relationship now is not "memory system fully replaces ContextManager", but "memory system is wired into ContextManager".

### 2. `extract_chapter_context.py`

The pre-write context script extracts several key sections from `ContextManager`, which already include:

- `reader_signal`
- `genre_profile`
- `writing_guidance`
- `plot_structure`
- `long_term_memory`

This means long-term memory has entered the main writing context, not staying in an isolated experimental script.

### 3. `MemoryContractAdapter`

`MemoryContractAdapter` is a thin external adaptation layer.

It wraps existing modules into a unified interface, providing:

- `commit_chapter()`
- `load_context()`
- `query_entity()`
- `query_rules()`
- `read_summary()`
- `get_open_loops()`
- `get_timeline()`

The meaning of this layer is: the current memory chain already has a stable interface, but the underlying storage still reuses existing `state / index / scratchpad / summaries`.

### 4. CLI

Current long-term-memory-related CLI is split into two categories:

- `webnovel.py memory ...`
- `memory_cli.py`

Common commands include:

- `memory stats`
- `memory query`
- `memory dump`
- `memory conflicts`
- `memory bootstrap`
- `memory update`

## Storage Responsibility Split

### `state.json`

Responsible for runtime state, not long-term knowledge accumulation.

Currently mainly carries:

- protagonist snapshot
- progress
- plot threads
- pending disambiguation

### `index.db`

Responsible for structured historical evidence.

Current long-term memory, when reading `episodic_memory`, mainly gets from here:

- state changes
- relationships
- appearance records
- part of reader-retention and review data

### `summaries/`

Responsible for chapter summaries and recent writing context.

In the long-term memory chain, it has two roles:

- as the recent-summary source for `working_memory`
- used in `bootstrap` to backfill "foreshadowing"-type open questions

### `memory_scratchpad.json`

Responsible for the long-term semantic memory cache, the current main source of truth for long-term memory.

### `project_memory.json`

Responsible for project-experience / learning accumulation, currently still an independent side path, not merged with `memory_scratchpad.json`.

## Key Capabilities Already Implemented

- Long-term memory already supports persistent read/write
- Already has unified schema, status enum, and bucket structure
- Already has conflict detection and simple status demotion
- Already has a compactor to prevent scratchpad unbounded growth
- Already can inject long-term memory into the main writing context
- Already has CLI query, backfill, and manual-update entry points
- Already has `MemoryContractAdapter` as a stable external interface

## Current Boundaries and Limits

### 1. Not a fully independent memory runtime

Still depends on:

- `ContextManager` for final assembly
- `index.db` for recent historical evidence
- `state.json` for runtime snapshot

### 2. `episodic_memory` leans recent, not full-history recall

Currently more like a "recent structured evidence layer", not a unified cross-book semantic recall system.

### 3. `semantic_memory` is still a JSON scratchpad

Currently no separate long-term semantic vector layer, nor a graph database layer.

### 4. `project_memory.json` and the long-term memory main chain are not yet unified

Project-experience memory and plot long-term memory are now two parallel data sources.

### 5. Conflict adjudication is still lightweight rules

Currently mainly:

- primary-key dedup
- old-value demotion
- conflict statistics

No heavier cross-chapter semantic adjudication flow yet.

## Conclusion

The long-term memory in the current repo has moved from "design discussion" to "runnable architecture" stage, but its real positioning should be:

- already wired into the main writing chain
- already has persistence, orchestration, consumption, and ops entry points
- still built on the existing `ContextManager + state/index/summaries` ecosystem

Therefore, this document only keeps the "current-state architecture explanation".

Historical plan documents have been removed; if it evolves further later, a new spec should be written separately based on the actual code state at that time.
